# Conversation Design

## 1. Goals

Airway IM uses one conversation model for both one-to-one direct messages and
multi-user group chats. The design must:

- expose the same conversation identifier format for direct and group chats;
- prevent duplicate direct conversations for the same pair of users;
- allow multiple group conversations with identical member sets;
- support membership history and group roles;
- work with horizontally scaled API and Gateway servers; and
- provide stable, per-conversation message ordering.

## 2. Conversation identifiers

`conversation_id` should be an opaque, globally unique identifier generated by
the server. The recommended format is ULID, represented as a 26-character
uppercase string:

```text
01J2Q7D4N5R8TK6VD3SZ1H0Y9M
```

UUIDv7 is also suitable if the project standardizes on UUIDs. Both formats can
be generated independently by multiple server instances and are approximately
sortable by creation time.

The identifier must not encode:

- whether the conversation is direct or group;
- user IDs or usernames;
- the number of members; or
- mutable properties such as the group title.

Keeping the ID opaque avoids leaking relationship information, keeps public
URLs stable, and allows the conversation model to evolve without changing its
identifier. Authorization must always be based on server-side membership data,
never on information inferred from an ID.

All APIs use the same `conversation_id` format regardless of conversation type.
For example, sending a message does not require the client to distinguish
between direct and group conversations:

```json
{
  "conversation_id": "01J2Q7D4N5R8TK6VD3SZ1H0Y9M",
  "content": "Hello!",
  "content_type": "text/markdown"
}
```

## 3. Data model

The following SQL is illustrative. Migrations must use the repository's schema
helpers and choose equivalent types for each supported database.

### 3.1 Conversations

```sql
CREATE TABLE conversations (
    id              CHAR(26) PRIMARY KEY,
    kind            VARCHAR(16) NOT NULL,
    title           VARCHAR(255),
    avatar_url      TEXT,
    created_by      BIGINT NOT NULL,
    next_sequence   BIGINT NOT NULL DEFAULT 1,
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL,

    CHECK (kind IN ('direct', 'group'))
);
```

The fields have the following meanings:

| Field | Description |
| --- | --- |
| `id` | Opaque ULID exposed as `conversation_id` in APIs. |
| `kind` | `direct` for a one-to-one conversation or `group` for a multi-user conversation. |
| `title` | Group title. Normally `NULL` for a direct conversation. |
| `avatar_url` | Optional group avatar. Normally `NULL` for a direct conversation. |
| `created_by` | User who created the conversation. |
| `next_sequence` | Next message sequence number within this conversation. |
| `created_at` | Server-assigned creation time. |
| `updated_at` | Last metadata update time; it should not be used as the canonical last-message time. |

The database should enforce the allowed values for `kind`, with an application
validation fallback where a database does not support `CHECK` consistently.

### 3.2 Conversation members

```sql
CREATE TABLE conversation_members (
    conversation_id CHAR(26) NOT NULL,
    user_id         BIGINT NOT NULL,
    role            VARCHAR(16) NOT NULL DEFAULT 'member',
    joined_at       TIMESTAMP NOT NULL,
    left_at         TIMESTAMP,

    PRIMARY KEY (conversation_id, user_id),
    FOREIGN KEY (conversation_id) REFERENCES conversations(id),
    CHECK (role IN ('owner', 'admin', 'member'))
);

CREATE INDEX conversation_members_user_id_idx
    ON conversation_members (user_id, conversation_id);
```

This table is used for both direct and group conversations. A direct
conversation has exactly two member rows. Group conversations may have two or
more active members, depending on product policy.

An active member has `left_at IS NULL`. When a user leaves a group, the server
sets `left_at` instead of deleting the row. This preserves membership history
for authorization, audit, and message visibility decisions. If rejoining must
preserve every join/leave interval, membership periods should be moved into a
separate history table; otherwise rejoining can clear `left_at` and update
`joined_at` according to the product's history policy.

Roles primarily apply to group conversations:

- `owner` can manage the group and transfer ownership;
- `admin` can perform delegated group-management operations; and
- `member` can participate according to group policy.

Direct-conversation members use `member`. Blocking, muting, archiving, and
deleting a conversation from one user's view are user-specific settings and
must not change the conversation ID or delete the other user's membership.

## 4. Direct conversations

### 4.1 Uniqueness rule

Airway IM should normally have at most one direct conversation for an unordered
pair of users. Requests from user 10 to user 20 and from user 20 to user 10 must
resolve to the same conversation.

Store a normalized user pair in a separate table:

```sql
CREATE TABLE direct_conversations (
    conversation_id CHAR(26) PRIMARY KEY,
    user_id_low     BIGINT NOT NULL,
    user_id_high    BIGINT NOT NULL,

    UNIQUE (user_id_low, user_id_high),
    FOREIGN KEY (conversation_id) REFERENCES conversations(id),
    CHECK (user_id_low < user_id_high)
);
```

Before lookup or insertion, always normalize the pair:

```go
userIDLow := min(currentUserID, targetUserID)
userIDHigh := max(currentUserID, targetUserID)
```

The database uniqueness constraint is mandatory. An application-only
"check then insert" is subject to races when two users or two API instances
create the same direct conversation concurrently.

### 4.2 Creation algorithm

The direct-conversation creation endpoint should behave as a get-or-create
operation:

1. Authenticate the requesting user and validate the target user.
2. Reject a request in which both user IDs are the same unless a saved-messages
   conversation is introduced as a separate feature.
3. Normalize the two IDs as `user_id_low` and `user_id_high`.
4. Look for an existing `direct_conversations` row and return it if found.
5. Otherwise, begin a database transaction and create a `direct` conversation,
   its normalized pair row, and its two membership rows.
6. Commit the transaction and return the new conversation.
7. If the normalized-pair insert loses a uniqueness race, roll back the new
   records, query the winning row, and return that conversation instead.

The operation is idempotent from the caller's perspective: concurrent or
repeated requests for the same pair return one canonical `conversation_id`.

Do not derive the public ID from a hash such as
`hash(min_user_id + ":" + max_user_id)`. A deterministic ID can expose account
relationships and complicates tenant isolation, account merging, key rotation,
or future support for more than one type of direct conversation. An independent
opaque ID plus a private unique mapping is safer and more flexible.

### 4.3 Direct-conversation lifecycle

A direct conversation normally remains canonical even if one user hides,
archives, or blocks it. Starting a chat with the same user later should return
the existing ID and preserve history subject to retention policy. Blocking is
checked when sending and delivering messages; it should not create a second
direct conversation.

If the product later requires permanently separate direct-message threads for
the same two users, the uniqueness key must explicitly include a thread or
generation value. That is a different product model and should not be inferred
from the public ID.

## 5. Group conversations

Every group creation request generates a new `conversation_id`. Two groups may
have the same title and exactly the same members because their identity is not
derived from membership.

An example request is:

```http
POST /api/v1/conversations HTTP/1.1
Authorization: Bearer 125e07c7e47732b73ae00b3f86bac7aa
Content-Type: application/json
```

```json
{
  "kind": "group",
  "title": "Airway IM Backend",
  "member_uuids": ["user-2", "user-3", "user-4"]
}
```

The server creates the group transactionally:

1. Generate a new ULID.
2. Insert a `group` conversation.
3. Add the authenticated creator as `owner`.
4. Validate, deduplicate, and add the requested users as `member`.
5. Record an outbox event for conversation creation.
6. Commit, then publish the event asynchronously.

Membership changes must be authorized and transactional. A group must have
exactly one active owner. Removing or deactivating the owner therefore requires
an ownership transfer or an explicit group-dissolution operation.

Adding members to an existing group follows these rules:

- only an active `owner` or `admin` may add members; direct conversations
  reject membership changes outright;
- the request is idempotent — already-active members are skipped, duplicates
  and the caller's own ID are removed before validation, and every added user
  must exist;
- a former member rejoins by clearing `left_at`, refreshing `joined_at`, and
  resetting the role to `member` (elevated roles are never restored
  implicitly); and
- the insert/rejoin and the `conversation.member_added` outbox event commit in
  one transaction; the event targets every active member, including the ones
  just added, so online clients can refresh their member list in real time.

Removing a member follows the mirror-image rules:

- only an active `owner` or `admin` may remove; an `admin` may remove only
  plain members, never other admins;
- the owner can never be removed — a group must always have exactly one
  active owner, so removal requires an ownership transfer first;
- callers cannot remove themselves (a leave operation is a separate feature);
- removal sets `left_at` and is an idempotent no-op for users who are not
  active members; and
- the `conversation.member_removed` outbox event commits in the same
  transaction and targets every active member **plus the removed user**, so
  the kicked client's UI can react immediately.

## 6. API representation

Both conversation types use a common response shape:

```json
{
  "id": "01J2Q7D4N5R8TK6VD3SZ1H0Y9M",
  "kind": "direct",
  "title": null,
  "avatar_url": null,
  "members": [
    {
      "user_uuid": "user-42",
      "role": "member",
      "joined_at": "2026-07-20T10:00:00Z"
    },
    {
      "user_uuid": "user-43",
      "role": "member",
      "joined_at": "2026-07-20T10:00:00Z"
    }
  ],
  "created_at": "2026-07-20T10:00:00Z",
  "updated_at": "2026-07-20T10:00:00Z"
}
```

For a direct conversation, the client derives display information from the
other member's current user profile. The server should not persist a synthetic
direct-chat title or avatar in `conversations`. For a group, `title` and
`avatar_url` describe the group itself.

The server may omit or paginate `members` in conversation-list responses for
large groups. That optimization does not change the identity model.

## 7. Message ordering

Message IDs and timestamps alone must not define strict conversation order.
When creating a message, the server atomically allocates the next
`sequence` from its conversation and stores it with the message:

```text
(conversation_id, sequence)
```

The pair must be unique. `sequence` is monotonically increasing only within one
conversation; it has no meaning across conversations. Clients use it to order
messages, detect gaps, and request missed messages after reconnecting.

The allocation and message insert must occur in the same transaction. An
implementation may lock the conversation counter row, use an atomic database
update that returns the allocated value, or use another database-supported
sequence-allocation technique. It must not calculate the next value with an
unlocked `MAX(sequence) + 1` query.

Gaps are acceptable if an allocation can be committed independently, but
duplicate sequence values are not. If gap-free ordering is required, allocate
the number in the same transaction that inserts the durable message and its
outbox event.

## 8. Authorization rules

Every operation loads conversation type and membership from trusted storage.
At minimum:

- only an active member may read or send messages;
- group administration requires the appropriate active role;
- direct conversations must always map to exactly two distinct users;
- clients cannot choose `created_by`, roles, or membership timestamps;
- a valid `conversation_id` does not by itself grant access; and
- WebSocket routing must use the same membership and visibility rules as HTTPS
  APIs.

Whether former group members may read messages sent before they left, and
whether new members may read messages sent before they joined, are explicit
product policies. The server can enforce them using `joined_at`, `left_at`, and
message timestamps or sequences. These policies must not be left to clients.

## 9. Recommended invariants

The implementation and its tests should enforce these invariants:

- every conversation has one opaque server-generated ID;
- `kind` is immutable after creation;
- a direct conversation has exactly two distinct members;
- one normalized user pair maps to at most one direct conversation;
- a group has exactly one active owner;
- identical group memberships do not imply identical conversations;
- membership history is not destroyed by a normal leave operation;
- `(conversation_id, sequence)` uniquely identifies a message position; and
- authorization never depends on parsing `conversation_id`.
